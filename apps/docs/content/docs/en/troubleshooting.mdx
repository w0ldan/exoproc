Treat an error together with the stage where it occurred. NThread, accessors, and hooks operate on the same target process, so one timeout symptom can have different causes.

For `NoSleepAddressError`, `NoPushretAddressError`, or `NoJumpAddressError`, verify Windows x64, `ntdll`/`kernel32`/`kernelbase`, and completed async initialization. For `CallTimeoutError`, inspect the address, signature, thread state, and suspend ownership before increasing the timeout. For `CallThreadDiedError`, use a fresh target and isolate the call with a small returning function.

If `expectedRsp` is set, both `call()` and `callSync()` warn on a return-stack mismatch. Record PID, driving thread ID, target address, first bytes, argument types, `RIP`, `RSP`, argument registers, result register, timeout result, and thread exit state in hexadecimal-safe form.

## CI / Wine environment issues

### `VirtualAlloc`/`malloc`/`fopen` on a freshly-created thread is unreliable (GitHub Actions only)

On GitHub Actions' virtualized Wine runners (never on real hardware), real WinAPI/CRT calls (`VirtualAlloc`, `malloc`, `fopen`, ...) executed on a thread that was just created are unreliable, whether local or remote. `Native.Thread.create()` delivers a corrupted `lpParameter`; local `VirtualAlloc` fails with `ERROR_INVALID_PARAMETER`. Also, `RemoteCallableMemoryAccessor.call()`/`callSync()` uses `CreateRemoteThread`'s single-argument (`lpParameter`) start routine, so it must **never be called with more than one argument** — arguments past the first are silently dropped.

**Fix:** spawn a real process (`new TestProcess()`), grab one of its existing threads (`Native.Thread.getThreads(pid)[0]`), and drive all calls through `IndirectNThreadHostAccessor(pid, tid)`. This hijacks that already-live thread's register context (`SetThreadContext`/`ResumeThread`), bypassing `CreateThread`/`CreateRemoteThread`/local `VirtualAlloc` entirely. If a real thread genuinely must enter the hooked function as its actual entry point, bake the argument in as a compile-time literal in a `cmachinecode()` wrapper instead of relying on `lpParameter`.

### Intermittent Bun segfault on the full local Wine suite

`bun-wine test` can occasionally crash Bun itself (Wine-specific, roughly 1-in-4 to 2-in-5 per run). Two known root causes are fixed:

- **Double `CloseHandle`:** an accessor sharing `TestProcess`'s handle via `{ handle: tp.handle }` without `closeHandle: false` gets its handle closed twice (once by the accessor, once by `tp.stop()`) — fatal under Wine. Rule: any accessor sharing `tp.handle` must pass `closeHandle: false` (or don't share the handle at all and let the accessor `OpenProcess` its own).
- **`RemoteCallableMemoryAccessor` argument drop:** same root cause as above — a multi-argument call routed through `CreateRemoteThread`'s single `lpParameter` slot leaves later arguments as register garbage, which can crash with a page fault. Move to `IndirectNThreadHostAccessor`.

### Cross-package `src/` imports can resolve to a stale `dist/` build

Every package's `package.json` `"main"` points to `./dist/index.js`, not `./src/index.ts`. Files under `tests/` see live `src/` via tsconfig `paths`, but a package's own source importing another package (e.g. `packages/nthread/src/*.ts` importing `bun-xffi`) resolves through the `node_modules` symlink to the **built** `dist/`. **After editing a `packages/*/src/` file that another package imports across the workspace boundary, run `bun run build` before trusting a Wine test result that touches the consuming package** — a clean typecheck/lint doesn't guarantee this, since both only ever see live `src/`.

### `instanceof` against a class from another package is unreliable under Wine

Bun's isolated linker gives every consuming package its own `node_modules/<dep>` symlink (all pointing at the same directory). Under `bun.exe` via Wine, each distinct symlink path is evaluated as a separate module instance, so the same class imported through different packages can fail an `instanceof` check. Assert by `instance.constructor.name` instead. `instanceof` checks against a class declared in the _same_ package as the code under test remain reliable.

### A test run with no output that never returns usually means a leaked process from a prior run

`bun-wine test` can hang indefinitely with zero stdout. Usually a prior run's `bun.exe` died without its spawned `ping.exe` child exiting, and that orphan still holds a handle to the old stdout pipe. Check `ps -eo pid,ppid,stat,etime,pcpu,cmd | grep -iE "wine|ping.exe"` for leftovers from a previous run and `kill -9` them (a stray process pegged at high CPU can also starve the Wine scheduler and cause unrelated tests to time out).
